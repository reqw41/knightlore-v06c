# Рецепт переноса Filmation-игры (Knight Lore → Alien 8) на Вектор-06Ц

Шаблон, снятый с Knight Lore. Alien 8 — тот же движок (Ultimate 1985, ZX 48K), делать по тем же шагам.
Все инструменты лежат в этом репозитории и в `~/projects/knightlore-research`.

## 0. Что нужно на входе
1. **Дизассемблер ZX-версии с метками** (для Alien 8 — искать у tcdev/jonsole; если нет, делать по
   Knight Lore: те же процедуры, те же имена, сверять сигнатурами первых байт функций).
2. **Оригинальный снимок** (.z80/.sna, archive.org) — оракул. Снимок может стоять в BASIC `PAUSE 0`:
   любая клавиша снимает паузу.
3. **CPC-версия** (Mode 1, 4 цвета) — источник палитр комнат и 2-битных спрайтов (шаг «цвет»).

## 1. Разведка (1 день)
- `zx-stand/`: MAME `spectrum` + `-dump снимок`; профиль тактов через отладчик:
  `-debug -debugger none`, из Lua `debugger:command('trace f.tr,0,noloop,{tracelog "%d,", totalcycles}')`.
- Найти и записать ВСЕ точки соприкосновения с железом ZX (grep по исходнику):
  * `in a,(0xFE)` (клавиатура, `read_port`), `out (0xFE)` (бипер, бордюр);
  * прямые писатели экрана: `zx_vram`/`zx_aram`, `screen_calc_addr_de`, `attrib_calc_addr_de`,
    `update_screen`, `blit_to_screen`, `clr_bitmap_memory`, константы `0x4000/0x5800/0x57xx`;
  * **самомодифицирующийся код**: `ld (метка+N),a`, `DB 0xCB` и прочие опкоды как данные, `jr` с
    патчуемым смещением (`print_sprite`), `djnz $` (правки jonsole);
  * **константы страниц** памяти в коде: `or 0xF0` (таблицы сдвига в print_sprite!), `high vidbuf`;
  * метки-ограничители таблиц (`font` = конец graphic_objs_tbl);
  * `ld sp,переменная` / `ld sp,hl` (стек под переменными и в данных спрайта);
  * `ld a,r` (случайность) и чтение памяти по адресу-счётчику (`seed_3 += mem[seed_2]`).
- Замер бюджета: итераций/с, такты по процедурам (рендер / сортировка / копия / задержка / звук).

## 2. Раскладка памяти Вектора (ч/б, одна плоскость)
```
0x0000 boot (di; ld sp; jp vec_boot)   0x0038 jp vec_pal_isr (RST 38h)   0x0040 vec_kbmat[8], vec_tmp
0x0060 vec_boot                         0x0100 код+данные игры (ORG после clear_end)
0x7A00 START/build_lookup_tbls (в оригинале лежат ВНУТРИ vidbuf — вынести!)
0x7B00 блок Вектора: vec_scan, vec_zxmap, ВИ53, screen_calc/blit/update_screen   стек ↓ от 0x8000
0x8000-0x9FFF ПЛОСКОСТЬ 0 (видимая)     0xA000-0xBFFF ПЛОСКОСТЬ 1 = БУФЕР в раскладке экрана (нативный рендер)
0xC000-0xC7FF ЗАЩИТНАЯ ЗОНА (вылет спрайтов/стираний за столбец 31 + временный стек `ld sp,seed_1`)   0xC800 переменные
0xCE00 zx_vram/0xE600 zx_aram (мусорное ОЗУ для атрибутов)   0xE900 очередь звука (256 Б + 5 Б)
0xF100 reverse_bits_table, 0xF200 shift_bits_table — НА МЕСТЕ (print_sprite адресует `or 0xF0`)
```
Правило: любой сегмент, куда игра пишет как в «экран ZX», должен существовать как ОЗУ; любой код,
лежащий в буфере, вынести; палитра игнорирует плоскости 1–3 => там можно держать данные.

## 3. Склейка (tools/kl_z80_to_8080.py, `kl_vec_glue`) — по одному пункту на железо
| железо ZX | что сделать на Векторе |
|---|---|
| загрузка | `.r0m` 64К с PC=0; `out (0),0x88`; палитра ТОЛЬКО в VBlank (RST 38h, флаг готовности), затем `di` навсегда; `out (2),0` бордюр; `out (3),0xFF` скролл; очистить плоскость |
| экран | НАТИВНЫЙ БУФЕР: плоскость 1 в раскладке экрана, адрес = база + (X/8)*256 + (32+Y), Y растёт вверх (0 = низ). print_sprite: `inc bc`→`inc b` (шаг вправо +256), переход строки `B -= w-1; inc c` (патч-значение = w-1 вместо 33-w), пиксельный цикл под `di/ei` (SP уходит в данные спрайта). vidbuf_calc_addr_*, fill/clear_window, print_8x8 (`dec l`, следующий символ +0x108), константы `vidbuf+N` (row*32+col → col*256+32+row) переписаны; blit/update_screen — сплошные столбцы; экран = буфер − 0x2000 |
| прерывание | RST 38h включён ВСЕГДА: ISR (push af/bc/de/hl на стек игры) грузит палитру по запросу и сканирует клавиатуру в VBlank — порт 3 (скролл = выбор ряда!) трогать вне VBlank нельзя, иначе кадр дёргается |
| атрибуты | ничего не делать: zx_aram — обычное ОЗУ |
| клавиатура | матрица `vec_kbmat[8]` заполняется в ISR (`vec_scan`: порт 0 = 0x8A, порт 3 = ряд, порт 2 = данные, назад 0x88 + скролл 0xFF + бордюр 0); `read_port(A=маска рядов)` только сводит её по таблице ZX-ряд→(ячейка,маска) 8×5; стрелки зеркалятся в Z/X/A/Q |
| бипер | ОЧЕРЕДЬ: `play_note`/`snd_delay`/`toggle_audio_hw(_xC)` только кладут запись (делитель ВИ53, длительность в 1/256 кадра = 26·N·периодов/273) и возвращаются сразу; ISR раз в кадр списывает 256 тиков и переключает ВИ53 (`vi_snd`); `play_audio_until_keypress` = вся мелодия в очередь + ждать клавишу + `vec_snd_flush`. Игра больше не стоит на звуке (стала быстрее — сценарии по времени меняются). Прежний вариант — частота: `toggle_audio_hw(B)` и `play_note(BC)` программируют ВИ53 канал A (`out (8),0x36`, делитель = N*11 + N/8; N — итераций djnz полупериода; 26 тактов/период на 3.5 МГц, ВИ53 1.5 МГц), длительность держат родные циклы задержки (игра стоит, пока звучит, как в оригинале); выключение — повторное управляющее слово. Звук НЕ в прерывании — перенос в ISR = отдельная переделка звукового движка |
| бордюр ZX | `out (0xFE)` убрать |
| ограничители таблиц | `font` -> `clear_end` (3 сайта) |

## 4. Сборка и прогон
`./build.sh z80vec` → `build/knightlore_z80.r0m`; `tools/emu80_run.sh z80` (Emu80, `vector.z80`, MCP 19785);
`tools/emu80_mcp.sh screen|kbd_send|cpu_state|mem_read|bp_set`. Меню: «0» старт; Z/X поворот, A вперёд, Q прыжок.
Типовые симптомы: перевёрнутая картинка = знак строки; «пунктирные» спрайты = таблицы сдвига не на месте;
чёрный экран + PC в мусоре = блок в нулевой странице перекрыт кодом (ORG 0x0100); синий мусор = палитра
записалась не в VBlank; полоска мусора в углу = стек в видимой плоскости.

## 6. Цвет (после i8080)
Две плоскости (4 цвета), палитры комнат по `attr&7` из CPC-дампа, спрайты CPC 4 px/байт

## 7. Грабли нативного буфера (столбцового), найденные на Knight Lore
- **Вылет за столбец 31**: объекты у правого края дают ширину рисования/стирания за 32-й байт; в линейном
  буфере ZX это заворачивало на следующую строку, в столбцовом — пишет в СЛЕДУЮЩУЮ СТРАНИЦУ. Держать за буфером
  защитную зону ≥2К, а blit/fill клипить на столбце 31 (иначе blit пишет в сам буфер).
- **Нулевые прямоугольники**: fill/blit с B=0 или C=0 крутят 256 итераций и стирают память — выход по нулю.
- **Временный стек `ld sp,seed_1`**: страница под переменными должна быть свободной (не буфер!), иначе адреса
  возврата затираются и игра «перезапускается» (прыжок на 0 → загрузчик → меню с 5 жизнями).
- Как ловить: Emu80 `bp_set {"type":"exec","addr":1}` (десятичный адрес!), при останове читать стек по SP —
  нули или данные вместо адресов возврата = затёртый стек. `cpu_state` в остановленном состоянии содержит
  сырой TAB — JSON разбирать с `strict=False`. В zsh переменные не разбиваются по пробелам: `${=VAR}`.

## 8. Цель `vec` (i8080 + Вектор) — что сломалось при рекомпиляции и как чинить
- **Хелперы `(ix+n)` в стек**: `call il_ix_xxx` + байт смещения — хелпер делает pop/push. Любой `ld a,(ix+n)`
  ПОСЛЕ `ld sp,hl` (print_sprite: SP указывает на данные спрайта) пишет адрес возврата и push хелпера в
  спрайт (порча начинается с spr−2). Читать все `(ix+n)` ДО смены SP (`kl_logic_fixes` переставляет
  `ld a,(ix+25)` перед `ld (tmp_SP),sp`). Симптом: первый спрайт (рамка меню) с заголовком-мусором,
  ширина 11, прыжок диспетчера мимо таблицы, перезапуск.
- **Регионы кода**: sjasmplus молча накладывает `ORG` друг на друга. Блок хелперов (1.1К) упёрся в таблицы
  0xF100, которые `build_lookup_tbls` перезаписывает — IY-хелперы стёрлись, `shuffle_objects_required`
  ушёл в нулевую страницу (nop до `vec_boot` = «перезапуск»). Теперь хелперы в нижнем регионе (0x7421),
  на границах стоят `ASSERT $ <= …` (стек 0x7E00, таблицы 0xF100, очередь звука 0xD400).
- **Диагностика перезапуска**: bp exec на 0x0083 (первый nop после scratch) ловит прыжок в нулевую страницу;
  адрес возврата на стеке = `call il_iy_xxx` + байт → по листингу видно вызывающего.
- Карту меток брать из `.sld` (поле 5 — адрес, поле 7 — `,имя,…`), а не из старого файла: адреса плывут.
- Темп i8080-сборки в Emu80 (счётчик итераций стабом в нулевой странице): 15.6 итер/с в покое, 14.4 при ходьбе
  (192–209К тактов/итерацию); Z80-сборка с нативными процедурами — 24.

## 9. Звук: как выверять тон и длительность (ВИ53 против бипера ZX)
- Период ноты ZX измерять в MAME точками останова на `out (0xFE)` с `logerror "%d",totalcycles` (журнал
  ограничен ~3500 строк консоли — писать в error.log через `-log`). МНК по нотам: период = 26.09·N + 111 T
  (N = B + 256·(C−1) — счётчик djnz-полупериода; `dec c` даёт по 256 на проход). Делитель ВИ53 при 1.5 МГц =
  период·3/7 = 11.19·N + 48; для `toggle_audio_hw` (один период = 26·B + 82 T) константа 35. Формула
  N·11+N/8 без константы давала +17…+47 центов (выше на малых N).
- Индекс `freq_tbl`: строка с меткой — это нота 0; парсер, пропускающий её, сдвигает все ноты на одну
  (полчаса ложной тревоги «MAME врёт на 6 %»).
- Умножение тики×периоды: множитель перебирать с МЛАДШЕГО бита (`rrca`), раз HL удваивается на шаге;
  `rlca` даёт зеркальный множитель (длительности в 3–8 раз длиннее).
- Очередь на 63 записи короче мелодии меню (89 нот): `play_audio` ждёт место, `play_audio_until_keypress`
  повторяет ZX (опрос клавиши между нотами, по концу данных — ждать тишины). После `vec_snd_room` A испорчен —
  перечитывать байт ноты.
- Проверка без слуха: bp на `shuffle_objects_required` (сразу после постановки мелодии старта) и сравнение
  очереди с расчётом по данным мелодии (делитель, тики) — должно совпасть байт в байт.

## 10. Атрибуты ZX прятали мусор — на Векторе его видно
Солнце/луна рисуется с X=176..225 в буфер, рамка (спрайты 0x5A/0xBA) маскирует только своё окно, blit берёт
столбцы 23..28; байты в столбцах 22, 29, 30 оставались в буфере и всплывали при `update_screen` (на ZX там
чернила = фон). Лечение: `vec_sun_save/restore` — сохранить эти столбцы (строки 0..30) до печати солнца и
вернуть после. Для Alien 8 искать такие места по всем спрайтам, рисуемым «за окном» с маской по атрибутам.

## 11. Звук MSX -> AY Вектора (сделано на Knight Lore, для Alien 8 повторять по этой схеме)
ZX-бипер даёт один голос и останавливает игру; у MSX-версии той же игры звук уже написан под
AY-3-8910 — его и переносим. Разбор оригинала: `~/projects/knightlore-research/msx/SOUND.md`,
данные `src/msx_tunes.bin` (490 Б), код `tools/kl_sound_ay.py`.

**Железо.** `out (0x15)` — номер регистра AY, `out (0x14)` — данные (чтение — с 0x15, не с 0x14).
Таблицу периодов MSX брать КАК ЕСТЬ: 1.775 / 1.789772 МГц = −14.35 цента одинаково на всех
нотах, строй сохраняется, а пересчёт даёт ошибку округления до 10 центов — то есть хуже.

**Формат.** Байт потока: биты 0–5 нота, 6–7 множитель длительности — тот же, что на ZX, поэтому
данные MSX ложатся на движок один в один (мелодии menu и game over вообще побайтно совпадают с ZX,
но у MSX есть второй голос, которого на ZX нет). Ноты 0–7 «накрыты» таблицей команд MSX: пустой
канал-заглушка пишет её слова в регистры тона с громкостью 0. Таблицу периодов делать на ноты
**0..63** (128 Б = 16 Б таблицы команд + 112 Б периодов), тогда журнал записей совпадает с MSX
байт в байт даже на заглушке; таблица «с ноты 10» даст выход за границу на ноте 0.

**Темп.** У MSX проигрыватель — свободный цикл без привязки к кадру: 114 «проходов» за видеокадр
(живой замер, SOUND.md §2.4), 1024 прохода = 8.98 кадра. На Векторе тик = кадр, и за тик каждый
канал отматывает ровно 114 проходов: `rem=114; пока rem: если dur==0 — выборка (тратит 1 проход),
иначе dur -= min(dur,rem)`. Счётчик длительности 16-битный, остаток проходов переходит в следующий
кадр — суммарный темп совпадает с MSX без накопления ошибки (замерено: сдвиг кадра 0 на всей
мелодии меню, 499 записей). Таблица длительностей не нужна: старший байт = `((биты 6-7)+1)*4`.

**Эффекты.** Тик — из объектного цикла по разу на объект. В обеих играх объектов ровно 40, как на
MSX, поэтому масштабировать длительности (7..31 тика) не пришлось. Вставлять сразу после
`ld sp,seed_1` в `update_sprite_loop` (стек уже известен), а НЕ в `ret_from_tbl_jp` — его тело
целиком подменяет `kl_native`. Глушение AY в конце игрового кадра (MSX 0x4136) — в `loc_B000`,
под проверкой «мелодия не играет». Приём оригинала «эффект кончился -> `inc sp/inc sp`, чтобы не
возвращаться своему вызывателю» на i8080 воспроизводить явным ветвлением.

**Грабли, которые стоили времени:**
- **Мелодию поверх игрового цикла играть нельзя.** Под `di` в `print_sprite` (SP уходит в данные
  спрайта) Вектор ТЕРЯЕТ кадровые прерывания — они не защёлкиваются. Мелодия старта отставала
  ровно на 20 % (172 кадра вместо 144), значения при этом совпадали идеально. Лечение —
  `play_audio` ждёт конца мелодии, как и делает оригинал (там проигрыватель блокирующий).
  Мелодии, играющие в покое (меню, game over), совпадают с MSX и без этого.
- **Порядок записей внутри выборки:** период lo, период hi, затем громкость по режиму (для режимов
  3/4 — 0x10 и следом R13=0). Команда «пауза» (4) пишет громкость ДВАЖДЫ: сначала по режиму, потом
  явный ноль. Любая перестановка ловится сверкой.
- **При завершении эффекта R7 НЕ пишется** — обновляется только тень микшера. Пишешь R7 — получаешь
  лишнюю запись в журнале и расхождение с моделью.
- Заголовки мелодий — абсолютные адреса MSX; при переносе пересчитывать в свой пул потоков
  (`адрес − 0x46C8 + msx_stream`), а мёртвую мелодию 0x46BC выбросить.

**Крючки.** Имена ZX-процедур сохранять, менять только их тела — тогда ни один сайт вызова не
трогается. Соответствие «какой ZX-звук = какой эффект MSX» устанавливается сверкой кода ПЕРЕД
каждым вызовом звука в MSX (в Knight Lore таких 22) с тем же местом ZX-исходника; три опорные
формулы, по которым проверяется вся таблица: эффект 7 берёт период из `~((ix+1)+(ix+2)+(ix+3))`
(= ZX `audio_B467`), эффект 4 — из `~(ix+3)` (= `audio_B451`), эффект 3 считает громкость из
координат игрока ровно как ZX `loc_B4D1`. Где одна ZX-процедура на MSX разошлась по разным
эффектам — разводить адресно по уникальному контексту сайта (`call M, audio_B451` и т. п.).
Где на MSX звука нет — ставить `ret` и перечислять в отчёте, а не выдумывать.

**Проверка без слуха.** `tools/aytrace_vec.js` — headless vector06js, перехват `io.output` портов
0x15/0x14, RST7 раз в 59904 такта = кадр, журнал «кадр регистр значение».
`tools/aycheck.py` сверяет журнал с `msx_psg_model.py` ПОКАНАЛЬНО: у MSX проигрыватель обходит
каналы по разу за проход, у нас каждый канал отматывает свои 114 проходов подряд — глобальный
порядок записей разный, а последовательность внутри канала обязана совпасть байт в байт.
Скрипт сам находит старт мелодии по списку инициализации PSG и берёт ровно столько записей,
сколько даёт модель: любая посторонняя запись, вклинившаяся в мелодию, сразу вылезает
расхождением значения. Результат на Knight Lore: меню 499 записей, старт 79 — расхождений 0,
сдвиг кадра 0.

**Цена.** Драйвер + 490 Б данных вместо всего ZX-пути (freq_tbl 183 Б, четыре ZX-мелодии,
`play_note`/`snd_delay`, `toggle_audio_hw*`, очередь ВИ53): нижний регион 0x7AA6 -> 0x7BDE
(+312 Б, до предела 0x7E00 осталось 546 Б), регион 0xD200..0xD400 освободился целиком.
Такты: 142.1К -> 144.5К в покое, 200.7К -> 203.5К при ходьбе (+1.6 %/+1.4 % на итерацию).

## 12. Стековый вывод и бюджет di-блоков (сделано на Knight Lore, для Alien 8 повторять)
Столбец буфера сплошной (256 байт, строка 0 = байт 32), поэтому SP можно навести на столбец:
- **Заливка** — `sphl` на конец окна, `push de` (оба байта = значение): 5.5 такта/байт против 27.
- **Блит буфер→экран** — SP на начало окна, `pop de` + `mov m,e/inr l/mov m,d/inr l`: 17 против 39.
- Число операций на столбец известно на входе, поэтому цепочка развёрнута целиком, а вход в неё
  и хвост нечётной высоты считаются ОДИН раз на вызов патчем иммедиатов (`ld l,n`, `jp nn`, `ld hl,nn`).
  **Грабли:** вход = конец − N·(размер блока). У заливки блок 1 байт, у блита 5 — с «конец − N»
  картинка разъезжается с третьей итерации.
- Окна выше высоты цепочки (32 строки) — прежним байтовым циклом, без di: спрайты меню до 64 строк.

**Прерывание не защёлкивается** (`reference_vector06c_interrupt_not_latched.md`): обратный ход внутри
di теряется. Замер на стенде: БЕЗ бюджета 139 кадров из 514 (27 %) попадали внутрь di. Лечение —
`vec_di_budget`: счётчик 0 ВИ53 в режиме 0 (управление порт 0x08, счётчик 0x0B — адреса переставлены),
ISR перезаряжает 0xFFFF, перед каждым di-блоком защёлка (`out 0x08←0`) + два `in 0x0B`; если остаток
минус стоимость ниже порога — `ei/halt`. Кадр = 29952 тика (1.5 МГц = 2 такта CPU). Стало 0 потерь.
- Стоимость блока **мерить, а не прикидывать**: у print_sprite это 47.4 тика на байт-столбец с почти
  нулевым разбросом (цикл развёрнут); коэффициент 40 давал 22 потери из 749. Формула 48·w·h + 512.
- Цена бюджета: ~100 тактов на опрос + 3.3 % в halt (покой). Это плата за целый кадр.

## 13. Гейт картинки: чем локстеп не годится и обо что он спотыкается
Локстеп сверяет только переменные — вывод он не видит. `tools/screendiff_vec.js` снимает FNV-хэш
буфера (0xA000–0xBFFF) и экрана (0x8000–0x9FFF) на КАЖДОЙ итерации плюс финальный дамп 16К;
`tools/render_gate.sh <ревизия>` разворачивает эталон через `git archive` в `build/ref` и сверяет
побайтно в покое и по `inputs_alive`. Две ловушки, каждая даёт ложное расхождение:
1. **Ввод по кадрам.** Клавиши через матрицу Вектора видны игре в момент скана в ISR: сборка другой
   скорости читает их в другом кадре. В гейте `vec_zxbuild` заглушается (`ret`), ряды ZX кладутся
   прямо в `vec_zxrows` на границе итерации — как на локстепе.
2. **`seed_3 += mem[seed_2]`.** Игра подмешивает в случайное число байт памяти по адресу-счётчику
   (на ZX это экран, на Векторе — собственный код), поэтому ЛЮБОЙ сдвиг кода меняет всю случайную
   последовательность. В гейте этот байт гасится (`86 add a,(hl)` → `00`) одинаково в обеих сборках.
Если расхождение всё-таки есть — искать журналом записей в 0x8000–0xBFFF и в переменные: видно,
расходится картинка или сначала seed (у нас первое расхождение было в seed_3 после 18187 совпавших
записей в буфер).

## 14. Замер темпа по платформам и по комнатам (как сравнивать честно)
- Метрика — итераций главного цикла в секунду: считать исполнения `ld (seed_2),hl` (одна и та же инструкция во всех
  версиях, ищется по опкодам `2a xx xx 23 22 xx xx 3a yy yy 86 85 84 32 yy yy`) за 250 видеокадров. ZX/CPC — MAME
  (`bpset …,{logerror "IT\n"; g}` + `-log`; ZX `zx-stand/zxspeed.lua`, CPC `cpc/cpc_speed.lua`), MSX — headless WebMSX
  (`msx/msx_speed.js`, дельта переменной 0xD802), Вектор — vector06js (`tools/profile_vec.js`, такты по слотовой модели,
  делить на 3 МГц) и Emu80 (стаб-счётчик в нулевой странице). Реальное время, поправка на тактовую не нужна; такты Вектора
  и T-состояния ZX напрямую не сравнивать.
- По комнатам: номер комнаты — полный байт 8 объектов 0 и 1 (бит 7 значим, валидных 128 из 256); подменять после
  init_start_location и до retrieve_screen (тап/хук на первую запись в буфер экрана внутри build_screen_objects при
  ненулевом байте). Вектор: `KLROOM=<n>` у профилировщика и `tools/roommap_vec.js` (карта всех комнат → build/roommap.csv);
  ZX `zx-stand/zxroom.lua` (ZXROOM=n); CPC `cpc/cpc_rooms.lua` (поле screen на CPC — 0x00DF/0x00FF, curr_room_attrib 0x0073:
  формула смещения переменных врёт, искать по коду `cp (ix+8)`); MSX `msx/msx_rooms.js` (0xDB05/0xDB25, хук bus.write,
  0xD80D — только триггер синхронизации, не атрибут).
- Стартовая комната у всех быстрая (ZX 22.4); честный бенчмарк — тяжёлые: 39, 163, 133, 31, 3 (см. таблицу в памяти проекта).
- Ловушка профиля: столбец «вызовов» — попадания PC в метку, головы циклов завышают; сравнивать сборки при ходьбе только
  на одинаковом числе итераций (ISR читает клавиши по кадрам, ускорение сдвигает сценарий).

## 16. Звук на ВИ53 (КР580ВИ53) — второй источник рядом с AY
AY есть не на каждом Векторе, ВИ53 есть на каждом. Поэтому драйвер MSX (§11) не переписан, а **раздвоен на выходе**:
он по-прежнему «пишет регистры AY», но `msx_wr` смотрит на байт `vec_snd_mode` — 0 шлёт в порты AY (0x15 номер,
0x14 данные), 1 кладёт значение в **зеркало** `msx_ayregs` (16 байт, ALIGN 16 — номер регистра складывается с младшим
байтом адреса без переноса). Раз в кадр ISR зовёт `msx_viflush`, и зеркало превращается в делители таймера.

**Порты ВИ53 на Векторе ПЕРЕСТАВЛЕНЫ** против даташита 8253: управление `0x08`, счётчики 0/1/2 = `0x0B`/`0x0A`/`0x09`.
Написать «как в даташите» — управляющие слова уйдут в счётчики и получится вой мимо нот. У i8080 нет `out (c)`, поэтому
порт счётчика подставляется в заготовку `msx_vistub` (`out (порт), a : ret` в ОЗУ, три байта).

**Пересчёт.** Такт таймера 1497600 Гц, AY Вектора 1.775 МГц с внутренним делением на 16 →
`делитель = период_AY * 13.5`, считается целочисленно как `13P + P/2` (`msx_ay2vi`). Проверка: 1497600/(13.5·P) =
110933/P против 1775000/(16·P) = 110937.5/P — 0.004 %, остальное даёт округление до целого (≤0.05 % на реальных нотах).

**Раскладка счётчиков** (`msx_viwant`, флаг `msx_vic0` = «счётчик 0 отдан музыке»):
- мелодия (`msx_play`=1) — игровой цикл стоит, `vec_di_budget` не зовут: все три счётчика под музыку, канал AY A/B/C →
  счётчик 0/1/2. ISR в это время НЕ перезаряжает счётчик 0 (проверка `msx_vic0` в самом начале `vec_isr`);
- игра (`msx_play`=0) — счётчик 0 держит секундомер бюджета di, эффектам остаются 1 и 2: канал B → счётчик 1,
  канал C → счётчик 2, канал A подхватывает тот из них, что в этом кадре молчит (сперва 2, потом 1). Если звучат и B,
  и C — **третий одновременный эффект отбрасывается**: у MSX три слота, у нас два счётчика. Канал A несёт только слот 0
  (чирп шара/огня и приземление), а слоты 1 и 2 (прыжок, падающие блоки, движущиеся объекты, шаги) сохранены полностью;
- переход «мелодия → игра» ловится в `msx_viflush`: он сам возвращает счётчику 0 управляющее слово 0x30 и заливает
  0xFFFF, чтобы `vec_di_budget` не прочитал остаток музыкальной ноты.

**Три приёма из King's Valley**, без которых звук плохой (см. `kvalley-v06c/src/v06c/vec_isr.asm`):
управляющее слово ПЕРЕЗАПУСКАЕТ счётчик — слать только при смене владельца; тишина = управляющее слово БЕЗ делителя
(счётчик встаёт), а не низкий тон; при возврате счётчика кэш делителя бить в 0xFFFF, иначе повтор той же ноты после
паузы не перезальётся и счётчик промолчит.

**Что теряется против AY** (у таймера один меандр на счётчик, без громкости):
- *громкость* — порог 6 из 15 (как в KV): тише = молчание, иначе тихие хвосты гудят наравне с мелодией;
- *огибающая* (режимы громкости 3 и 4, R13=0 = затухание за ~150 мс) — считаем громкость максимальной, пока бит 0x10
  в регистре громкости стоит: нота звучит полной длины и ровно, мелодия становится «органной». Пауза (команда 4) всё
  равно молчит: за режимом идёт явный ноль громкости;
- *шум* — у ВИ53 его нет. Шум в игре заказывает ровно один эффект (1 — приземление игрока, канал A). Отдаём ему
  падающий тон из периода шума: `делитель = R6*256`, R6 идёт 1→31, то есть 5850→188 Гц — короткий «шлепок» вместо
  щелчка тишины. Псевдошум LFSR (как в KV) не делали: дороже, а эффект живёт меньше кадра;
- *делители < 64* (выше 23 кГц) глушим: эффекты дают период 0..4, слышать там нечего, а счётчик они перезапускают.

**Почему хватает одного слива в кадр.** Эффекты тикают из объектного цикла по разу на объект — 40 тиков за игровую
итерацию, как на MSX. Итерация на Векторе идёт ~2.5 кадра (замер `screendiff_vec.js`: 504 кадра на 200 итераций), то есть
на кадр приходится ~16 тиков. Самый длинный эффект (31 тик) занимает ~2 кадра и попадает под 2–3 слива, шаги (23 тика) —
под 1–2. Каждый слив = одна слышимая нота 20–40 мс; на MSX эти эффекты звучат так же коротко. Мелодии тикают из ISR раз
в кадр, у них слив и тик совпадают один в один.

**Выбор источника.** `msx_snd_probe` в `vec_boot` пишет R1 (регистр 4-битный) значениями 0x0A и 0x05 и читает назад
**оба** порта: на MiSTer отвечает 0x15, в `vector06js` — 0x14 (там `ay.read(port & 1)` разведён наоборот), два разных
значения подряд отсекают залипшую шину. Нашли AY → `vec_snd_ask`=1, и `vec_snd_menu` перед `do_menu_selection` печатает
`SOUND  A AY  T VI53` (шрифт игры, буква = 0x09+номер, пробел 0x26, бит 7 = конец строки) и ждёт `A` или `T`; не нашли —
молча ВИ53. Вопрос задаётся один раз за загрузку и стирается до меню, поэтому картинку меню он не меняет.

**Как проверять.**
- `node tools/aytrace_vec.js build/knightlore_vec.r0m 1000 --snd=ay|vi --out=<регистры> --vi=<ВИ53>` — журнал записей
  снимается с точки входа `msx_wr` (C = регистр, B = значение), поэтому одинаков в обоих режимах;
- `python3 tools/aycheck.py <регистры> menu|start_game [кадр]` — 0 расхождений с моделью MSX
  (`knightlore-research/msx/msx_psg_model.py`) обязательно в ОБОИХ режимах;
- `python3 tools/vicheck.py <ВИ53> <регистры> [--expect=P,P,...]` — декодирует управляющие слова и пары байт делителя,
  сверяет 1497600/делитель с 1775000/(16·период) из зеркала (порог 1 %, на деле ≤0.05 %) и требует, чтобы указанные
  периоды встретились. Шаги игрока: ноты 37,39,40,42,40,39,37,35 → периоды 159/142/134/119/179 → делители
  2146/1917/1809/1606/2416;
- ходьбу гонять ТОЛЬКО через `--inputs=inputs_alive.txt` (стенд как в `screendiff_vec.js`): покадровый стенд с
  `--key0=` в игре разбегается и уходит в мусор около 1100-го кадра — проверено и на сборке ДО правок звука;
- все стенды цели `vec` кладут `vec_snd_force` до старта (1 = AY, 2 = ВИ53; `KL_SND=vi`). Без этого проба находит AY
  эмулятора и стенд виснет на вопросе. Гейт картинки от этого не страдает: эталон метки не имеет и идёт как раньше,
  а текущая сборка с `vec_snd_force`=1 ведёт себя ровно так же.

> **Статус цели `z80vec` (Z80-адаптер):** заморожена на коммите 80c96e3 (2026-09-10, звук MSX ещё бипер/ВИ53). Дальше нативные
> модули (`kl_native_logic`, стековый рендер) пишутся под i8080-цель, Z80-сборка их не получает и с e91aa70 не собирается
> (нет ячеек kl_lines/kl_ball_cc). Для Alien 8 Z80-этап нужен только как первая проверка склейки (экран/клавиатура/звук),
> после перехода на `vec` его можно не поддерживать. Темп Z80 на Векторе всё равно вдвое ниже i8080 (слоты шины).

## 17. Экономия памяти под два набора графики (ч/б ZX + цвет CPC)
Задача: в одном образе держать ч/б (одна плоскость) и цветной набор (две видимые плоскости +
двухплоскостной буфер), то есть под видео уходит 26–28К, а всё остальное должно уложиться в 36–38К.
Ниже — инструменты, замеры и цены, снятые на Knight Lore; для Alien 8 повторять по тем же шагам.

### 17.1 Инструменты инвентаризации
- `tools/sizemap_vec.py build/knightlore_vec.lst [минимум] [--all]` — байты каждой процедуры/блока
  из листинга, сводка по категориям и по регионам раскладки. KL: спрайты 15574, всё прочее 21022.
- `tools/coverage_vec.js` — покрытие: какие байты кода ни разу не исполнялись (меню + вход в комнату +
  игра по 6 комнатам). KL: холодных байт без спрайтов 15561, но ~7К из них — ДАННЫЕ (читаются, не
  исполняются): `location_tbl` 2432, `sprite_tbl`/`upd_sprite_jmp_tbl` по 376, `font` 320,
  `special_objs_tbl` 288. Реально холодного КОДА ~6–8К, и почти весь он нужен в других комнатах.
- `tools/shiftstat_vec.js` — статистика сдвигов `print_sprite` (см. 17.2).
- Ловушка: сравнивать темп между сборками по «тактов/итерацию» нельзя. Изменение времени сдвигает
  трассу ГСЧ, и комната играет другой сценарий: после вырезания атрибутов комната 39 дала +8 %
  тактов, но при этом `print_sprite` вызывался 922 раза вместо 861, а цена пикселя не изменилась
  (69.0 → 68.7 такта/байт выровненный путь, 93.6 → 93.5 сдвинутый). Судьи — `tools/render_gate.sh`
  (один и тот же сценарий) и цена за байт из `shiftstat_vec.js`.

### 17.2 Таблицы сдвига (3.5К) — ОСТАВИТЬ, замер
`print_sprite` берёт сдвиг из `(ix+26)&7` и адресует страницу таблицы константой `or 0xF0`:
7 сдвигов × 2 страницы (младший и старший байт `v<<s`, оба в дополнении) = 0xE00 = 3584 Б плюс
`reverse_bits_table` 256 Б. Замер (6 комнат по 100 итераций, `shiftstat_vec.js`):

| | вызовов | доля |
|---|---|---|
| выровненных (x&7==0) | 4743 | 65.2 % |
| сдвинутых | 2532 | 34.8 % |
| по сдвигу 1/2/3/4/5/6/7 | 65/79/293/1485/65/73/472 | 0.9/1.1/4.0/20.4/0.9/1.0/6.5 % |

Байт окна: выровненных 66.0 %, сдвинутых 34.0 %. Пиксельный цикл — 68.1 такта/байт на выровненном
пути и 93.6 на сдвинутом; сдвинутый цикл = 12.4 % всех тактов (без halt), выровненный 17.5 %.

Цена отказа от таблицы для сдвига s: без таблицы HL свободен, но на каждый исходный байт нужны два
16-битных сдвига (`add hl,hl` × s на каждое из двух значений) плюс перекладка через ячейки —
≈ 20·s + 30…80 тактов сверх нынешних 95. По байтам сдвига в самой тяжёлой по сдвигам комнате 39
(s1 3032, s2 3952, s3 6032, s5 3524, s6 4484 байт на 100 итераций при 30.6 М тактов без halt):

| вариант | освобождает | цена в комнате 39 |
|---|---|---|
| (а) таблицы только 4..7, цепочки для 1..3 | 1536 Б | +2.6…3.4 % |
| (а') таблицы только 3,4,7 (частые), цепочки 1,2,5,6 | 2048 Б | +5.1 % |
| (б) одна таблица на 1 бит + цепочка | ~3.1К | хуже (а): цепочка табличных обращений дороже `add hl,hl`, дополнение не композируется |
| (в) оставить как есть | 0 | 0 |
| (г) убрать таблицы только для s=1 и s=2 | 1024 Б | +1.6 % |

**Решение: (в) — оставить.** Порог «дороже 3 % темпа в тяжёлых комнатах — не делать» вариант (а)
уже пробивает, а даёт всего 1.5К. Вариант (г) в порог укладывается и держится в резерве: 1К за 1.6 %.
Отвергнуто также «одна таблица-ротация на сдвиг + маска» (7×256 = 1792 Б вместо 3584): каждое из
четырёх табличных обращений на байт получает лишний `or imm` и разъезжается на отдельные `ld a,(hl)` —
+36 % к сдвинутому циклу = +4.5 % общих тактов.

### 17.3 Атрибутная память ZX — выбросить (и это ещё чинит порчу спрайтов)
`attrib_calc_addr_de` считает адрес атрибута как `high(zx_vram+0x1700) + (0..3)`. После переноса
`zx_vram` на 0xCD00 это 0xE400–0xE7FF, то есть ВНУТРЬ верхнего региона кода. `clr_attribute_memory`
писала 768 байт 0x46 поверх `spr_091..spr_095` на каждую очистку экрана; ещё ~90 записей за 100
итераций давали `print_text` (по байту на символ), `display_object` (заливка 3×3), `colour_panel`.
Подстановка адреса в склейке была молчаливым no-op: шаблон искал `ORG 0xCE00`/`ORG 0xE600`, а в
исходнике стояло 0xCD00/0xE500 — **всегда ставить assert на число замен**.
Вырезано (`kl_cut_zx_attributes`): расчёт адреса, запись атрибута в `print_text`, заливка в
`display_object`, `print_days`, `print_lives_gfx`, `colour_panel`, `colour_sun_moon`,
`clr_attribute_memory`, `fill_attr`, пробег `cycle_colours_with_sound` (звук и задержка сохранены),
сегменты `zx_aram` и `zx_vram`. Цена: −32 байта кода, картинка байт в байт.

### 17.4 Раскладка «плоскость 2 свободна»
Под цветной HUD нужна полоса в плоскости 2 (0xC000–0xDFFF), поэтому кода/данных там быть не должно,
кроме защитной зоны спиллов 0xC000–0xC7FF. Сделано:
- переменные `clear_start..clear_end` (0x568, в т.ч. `graphic_objs_tbl` 40×32) 0xC800 → **0x7A80**;
  адрес обязан быть кратен 32, иначе ломаются ASSERT'ы на `graphic_objs_tbl & 31` (в KL — 8);
- стек: `SP = clear_start` и в загрузчике, и в `START` (было 0x8000 = плоскость 0). Главный стек и
  временный `ld sp,seed_1` растут вниз ОТ ОДНОГО адреса, поэтому им хватает одного буфера. Замер
  (`минимальный SP` по 6 комнатам + меню): главный 38 байт, временный 72 → зарезервировано 256;
- `zx_vram`/`zx_aram` удалены (17.3);
- начало верхнего региона — параметр `VEC_UPPER` (env `KL_VEC_UPPER`), потолок кода нижнего —
  `VEC_CODE_TOP`.

### 17.5 Как влезло: дыры вне картинки (сделано 2026-09-10)
Дефицит при `KL_VEC_UPPER=0xE000` был 2 352 байта (верх кончался на 0xFA30 при потолке 0xF100).
Закрыт БЕЗ платы за темп — местом, которого никто не видел.

**Дыры.** Картинка занимает строки 32..223 каждого из 32 столбцов плоскости (адрес = база +
столбец·256 + 32 + Y). Строки 224..255 столбца c и 0..31 столбца c+1 лежат в памяти подряд — это
64 непрерывных байта, куда не пишет ни рендер, ни очистка, а на экране они всегда чёрные (в
плоскости 0 там нули, а индекс палитры без бита p0 = чёрный при любых p1..p3). Плоскость 1
(буфер) и плоскость 2 (селектор белого HUD) дают по 2 048 байт таких дыр. Проверять замером:
`node tools/holescan_vec.js <rom> <sld> 200 <inputs>` печатает, какие строки каждой страницы
видеопамяти реально пишутся.

**Упаковщик** `vec_pack_holes` (kl_z80_to_8080.py) увозит туда мелкие процедуры нижнего региона.
Блок «метка: … ret/jp» движим, если: весь состоит из инструкций; кончается БЕЗУСЛОВНОЙ передачей
управления; предыдущий блок тоже (иначе в него проваливаются сверху) и непуст (иначе метка-синоним);
перед ним нет ORG. Длины инструкций считает `_i8080_len` — сверена с листингом (7 685 инструкций,
0 расхождений). Темп не меняется: у i8080 адрес процедуры на её скорость не влияет.
Грабли: `halt` — НЕ безусловная передача управления (после прерывания идём дальше), и в регулярке
терминатора надо схлопывать пробелы, иначе `jp\s+` отступает назад и «jp nz, x» проходит за
безусловный переход.

**Плата за дыры плоскости 1:** `clear_scrn_buffer` больше не трёт буфер сплошным `clr_mem`, а идёт
постолбцово по строкам 32..223 (+13 байт, зато 6 144 записи вместо 8 192).

**Разрез спрайтов** — параметр `VEC_SPLIT` (env `KL_VEC_SPLIT`, сейчас `spr_077`): с этой метки
хвост уезжает в верхний регион, ниже остаётся столько, сколько влезло. Спрайты адресуются через
`sprite_tbl`, разрез произволен; сдвигать при любом изменении размера кода (следить за ASSERT'ами
нижнего и верхнего региона: `python3 tools/regions_vec.py build/knightlore_vec.lst`).

### 17.5.1 Спиллы печати и белый HUD
Буфер Вектора столбцовый, поэтому печать за столбец 31 попадала не в левый край следующей строки
(как в ZX), а в плоскость 2 — и белила бы точки поля. `ps_cw` (kl_native_render.py) режет ширину:
`w' = min(w, 32 - столбец)`; обе цепочки занимают ровно w столбцов (выровненная — w групп по
столбцу, сдвинутая — w-1 групп плюс хвостовая запись), поэтому формула одна на оба пути и w' ≥ 1.
ГЛАВНОЕ: цепочка читает спрайт через SP, и укороченная цепочка не дочитывает 2·(w−w') байт строки —
без компенсации все следующие строки спрайта разъезжаются. Поэтому `ps_cw` патчит младший байт
перехода конца строки (`ps_jrow`) на `ps_fix`, который двигает SP за непрочитанный хвост (обе метки
в одной странице с цепочкой — ASSERT). Цена 0.35 % в тяжёлой комнате.
Маска белого — `vec_hudcols`: прямоугольники (страница столбца, столбцов, первая строка, строк).
Геометрия сверена с атрибутами оригинала (ярко-белый 0x47) и пересчётом «строка Вектора =
223 − пиксельная строка ZX»: жизни столбцы 2..5 строки 64..79, DAY и счётчик столбцы 15..18
строки 32..63, солнце/луна с рамкой столбцы 23..28 строки 32..63.

### 17.6 Спрайты: сколько дадут простые схемы (замер, не делать)
103 спрайта, 15 572 байта. Полных дублей нет. Байтовый RLE: −366 Б (2.4 %) на всём массиве,
−307 Б (2.0 %) поспрайтно — данные плотные, нулей 23.7 %. Дедупликация одинаковых СТРОК: строк 5356
(15 366 Б), уникальных 1971 (6 021 Б) — сами данные ужимаются на 61 %, но индекс по 2 байта на строку
стоит 10 712 Б, итог **−1 367 Б в минус**. С 11-битным индексом вышло бы ≈ +1.3К, но распаковка бит
попадает в горячий `print_sprite`. Вывод: 4К из спрайтов простыми средствами не достать, нужен
отдельный кодек (общие тайлы/пословный LZ) и своя оценка темпа.

### 17.7 Мелочи, которые окупаются
- Развёртка редких форм `(ix+d)`/`(iy+d)` вместо компактного хелпера: хелпер стоит 27..46 Б тела плюс
  4 Б (`call`+`db`) на обращение, развёртка — 13..18 Б. Порог подбирать ЗАМЕРОМ, а не моделью:
  для KL конец нижнего региона по порогу N≤0/1/2/3/4 = 0x7514/0x74BB/0x7439/0x7597/0x7597, то есть
  выгодны только формы с 1–2 обращениями. −219 Б и −0.35 % тактов (развёртка быстрее call+хелпера).
- Проверять реальную глубину стека эмулятором, а не «на глаз»: 512 зарезервированных байт против
  72 измеренных — 440 байт лежали зря.
